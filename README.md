# Amazing Pool

Рабочий гостевой MVP бильярда для браузера с интеграцией Telegram Mini App SDK (на реальных клиентах Telegram пока не проверен): React + TypeScript, настоящий 3D-стол на Three.js, общая физика и авторитетный WebSocket-сервер.

## Запуск

Требуется Node.js 22+.

```sh
npm ci
npm run dev
```

Интерфейс: `http://localhost:5173`. Vite проксирует `/ws` и `/api` на сервер `3001`. Оба сервера слушают `0.0.0.0`; браузер использует только адрес текущего сайта. Разрешён preview-домен `*.e2b.app`.

```sh
npm test       # 19 тестов физики, правил, интерполяции и онлайн-комнат
npm run build  # TypeScript + production-сборка
npm start      # один Node-сервер: сайт, /ws и /api/health; порт 3001
# PORT=8080 npm start
```

Установка production должна включать devDependencies: сервер запускается через `tsx`. `dist/` генерируется сборкой и не хранится в Git.

### Проверка игры вдвоём

1. Открой сайт в двух вкладках / браузерах / на двух устройствах.
2. В каждом окне нажми **Найти соперника** (на телефоне — **Играть онлайн**). В очереди только настоящие подключённые игроки, без искусственного счётчика и ботов.
3. Альтернатива: **Пригласить друга → Создать свой стол**. Скопируй ссылку нажатием на код комнаты или введи код на другом устройстве.
4. Прицел и удар разделены. Проведи по сукну — кий на столе повернётся вокруг битка (поворот относительный: кий не «прыгает» к пальцу). Удар делается **вторым кием, нарисованным сбоку от стола**: оттяни его назад и отпусти, чем дальше оттянул — тем сильнее. Кий на столе при этом только крутится. На широком экране остались ползунок силы и кнопка **Ударить**.
5. Кнопкой с глазом переключается вид: наклонный три четверти или строго сверху.
6. На широком экране кнопка разворота над столом открывает большой игровой режим (выход — та же кнопка или Escape). На телефоне и в Telegram матч сразу открывается на отдельном экране со столом во весь экран — в горизонтальной ориентации.

### UI-тесты

```sh
npx playwright install chromium
npm run test:e2e
```

Для окружения с уже установленным Chromium можно передать `CHROMIUM_EXECUTABLE_PATH`. Тесты проверяют два клиента, запрет чужого хода, открытие правил во время удара, выход из комнаты, создание приглашения, компактный Mini App на экране 390×844 (поворот в горизонтальный, поворот кия протяжкой, удар боковым кием, переключение вида, обвязка внизу экрана), сборку без сервера (ни одной попытки WebSocket, шары останавливаются сами) и мост Telegram SDK с моком. Скриншоты и временные артефакты исключены из Git.

## Что реализовано

- Плоская «мобильная» подача стола без единого блика: графитовые борта с белыми точками, серебряные накладки луз, чёрные лузы, яркое синее сукно с мягким световым пятном по центру и линией дома. Все материалы матовые (Lambert, без specular и без environment map), свет — широкий ambient плюс одна мягкая лампа сверху, от шаров остаётся только лёгкая тень. Текстуры генерируются в коде; картинки-заглушки не используются.
- Вращение шаров из рассчитанной угловой скорости. В тренировке — непосредственное отображение координат физики; в онлайне — линейная интерполяция с буфером 70 мс, без экспоненциального «догоняния».
- Прицел короткими полосками, без линии через весь стол: от битка не идёт ничего, у прицельного шара — толстая скруглённая полоска, подходящая к кругу-призраку, и вторая, выходящая из шара: куда он поедет после удара. Длина, толщина и прозрачность всех трёх меток собраны в объекте `AIM` в начале `src/Table.tsx`. Линии рисуются узкими полосками на сукне, а не GL-линиями: толщина задаётся в единицах стола и не зависит от плотности пикселей. Сила набирается оттягиванием бокового кия (ход 150 px = 100 %), после отпускания кий на столе делает замах и бьёт через 210 мс. Кий наклонён на 10°, поэтому при повороте он проходит над шарами и бортами, а не сквозь них.
- Два вида камеры: строго сверху (по умолчанию, объектив 15° — борта остаются параллельными, как на доске) и наклонный три четверти (36°). Переключаются кнопкой и запоминаются в localStorage.
- Рендер под телефон: буфер кадра в `devicePixelRatio` до 2×, текстуры шаров 1024×512 с максимальной анизотропией, сферы 48×32, карта теней 2048, тонмаппинг выключен — цвета показываются ровно такими, какими нарисованы. Шары матовые и без лака: любой блик съедал цифры на телефоне.
- Физика с базовым шагом 120 Гц и адаптивными подшагами на сильных ударах: столкновения с потерей энергии, отскоки от бортов и губок луз, скольжение → качение, шесть луз. Сервер интегрирует прошедшее монотонное время, а не количество вызовов таймера.
- Тренировка с готовой свободной расстановкой.
- Бот-соперник: играет по тем же правилам и тем же `shoot()`, что и человек. За столом в онлайне бота сажает сервер, а на статичной сборке без сервера целый матч с ботом считается прямо в браузере.
- Список открытых столов: каждый ожидающий игрок виден остальным вместе со ставкой, за которую играет. Подсесть можно одним касанием, быстрая игра сажает за самый старый стол с выбранной ставкой или открывает свой.
- Ягодки — внутренняя валюта и ставки (0 / 10 / 25 / 50 / 100). Оба игрока вносят ставку, банк уходит победителю; выход из начатой партии со ставкой отдаёт банк оставшемуся. Пополнение — звёздами Telegram.
- Случайный подбор 1 на 1, приватные комнаты, копирование ссылки, вход по коду.
- Авторитетная онлайн-физика: клиент передаёт только угол и силу. Сервер проверяет очередь хода, конечность чисел, движение шаров и окончание партии. Обновления до 30 Гц.
- Группы шаров, переходы хода, ранняя/правильная восьмёрка, возврат битка после лузы.
- Гостевое имя, локальная история законченных партий, переключение звука, правила и адаптивный интерфейс.
- Переподключение WebSocket, уведомления о потере соединения / выходе соперника, heartbeat, лимит размера сообщения, удаление незаполненных комнат через 30 минут.
- Действия клиента ограничены по частоте (100 мс), но выход из очереди или комнаты обрабатывается всегда: отменённый игрок не остаётся в очереди и его комната удаляется сразу. Если сервер не ответил на действие за 5 секунд, кнопка разблокируется с уведомлением.
- Клавиатурный фокус в диалогах, Escape, `prefers-reduced-motion`, сообщение при отсутствии WebGL.

## Модель удара и масштаб

Сила задаёт **начальную скорость одним импульсом** в момент контакта. После контакта никакой постоянной силы от кия нет. Центральный удар сначала вызывает скольжение; трение уменьшает поступательную скорость и раскручивает шар. Для идеального однородного шара переход в чистое качение происходит при `v = 5/7 · v₀`. Далее скорость уменьшается от сопротивления качению. После столкновений возможен обмен поступательной и вращательной энергией — скорость отдельного шара не обязана убывать монотонно, но трение не добавляет суммарную энергию.

Параметры в `shared/table.ts` и `shared/game.ts`:

- Игровая поверхность 8-футового стола: 2,24 × 1,12 м; диаметр шара 57,15 мм.
- `μ скольжения = 0,20`, `μ качения = 0,032`, `g = 9,81 м/с²`. Качение чуть «тяжелее» турнирного сукна (0,010–0,020) намеренно: иначе шары докатываются по полминуты, а это мобильная игра. Порог остановки `0,018 м/с`.
- Коэффициент восстановления шар–шар `0,96`, борт `0,80`.
- Максимальная начальная скорость `5,5 м/с`; шкала нелинейная для точности слабых ударов.
- Геометрия столкновений бортов/губок общая с отображаемой геометрией. На столе реальные вырезы луз и глубокие колодцы, а не чёрные кружки поверх сукна.

Шаги физики привязаны к реальному времени: кадр может «догнать» до 0,25 с, поэтому на слабом устройстве стол замедляется, а не превращается в слоу-мо.

Это **параметризованное приближение**, а не измеренная модель конкретного реального стола. Реальное сукно, борта и шары отличаются. Тесты проверяют начальную скорость, переход скольжения в качение, отсутствие прироста энергии от трения, независимость свободного движения от шага, отсутствие туннелирования и равномерную интерполяцию. Визуальное ощущение и производительность ещё требуют оценки на устройствах.

## Правила и ограничения MVP

Это **упрощённая восьмёрка**, а не турнирная реализация WPA. Первый правильный цветной шар определяет группу. Нужно сначала убрать свою группу, потом восьмёрку. В тренировке до восьмёрки нужно убрать все цветные. Заказ лузы, свободное размещение битка, обязательное касание борта, специальные правила разбоя и управление смещением наклейки кия (винт/оттяжка/накат) пока не реализованы. Удар всегда центральный. Угловая скорость и трение сукна рассчитываются, но это ещё не полная физика spin/english: нет прыжков, массе и тангенциального трения шар–шар.

Комнаты и очередь хранятся **в памяти одного процесса**. Перезапуск сервера / потеря соединения завершает текущую комнату, возобновления матча нет. Завершённые партии сохраняются только в localStorage данного браузера. Закрытая незаконченная партия не попадает в историю. Счётчик клуба показывает подключения, а не уникальные Telegram-аккаунты.

Бот играет по тем же правилам, но без тактики: он не играет в отыгрыш, не думает о позиции битка на следующий удар и не считает, что осталось сопернику. Это разминочный соперник, а не искусственный интеллект.

Это не готовый к массовому запуску сервис: нет постоянной БД, рейтинга, настоящих аккаунтов, таймера хода, распределённого матчмейкинга, защиты от накруток или восстановления партии.

## Бот-соперник

Пока живых игроков мало, играть не с кем — поэтому есть бот.

- **Кто он.** Обычный участник комнаты с именем и машинной «мордой» вместо аватара: видно, что это бот, он не притворяется человеком.
- **Как думает** (`shared/bot.ts`, чистая функция `planShot`): перебирает все пары «свой шар → луза», проверяет, что биток дойдёт до точки контакта и шар дойдёт до лузы, и выбирает самый прямой и близкий удар. Отдельно отбрасывает удары, после которых биток сам укатится в лузу. Если ничего не стоит — катится к ближайшему достижимому своему шару, чтобы не отдать фол. Выбранная линия размывается ошибкой по уровню мастерства (`BOT_SKILL = 0.62`).
- **Насколько силён.** На 30 партиях бот против бота: **забивает ~37 % ударов, фолит ~10 %**, партия занимает ~34 удара на двоих. Проигрывает и выигрывает — то, что нужно для разминки, а не непобедимая машина.
- **Где встречается:** кнопка «Сыграть с ботом» (в списке столов, в карточке ожидания и в меню мини-приложения), а в онлайне бот **сам подсаживается** к столу, за которым никто не появился 20 секунд (`BOT_WAIT_MS`). Ставка при этом настоящая: сервер списывает её с игрока и ставит столько же от заведения, победитель забирает банк.
- Приватные комнаты для друзей ботом не заполняются.
- Бот в онлайне всегда соглашается на реванш, поэтому «Сыграть ещё» срабатывает сразу.

Бот запускается на сервере (`planShot` в цикле комнат) и в клиенте (режим `bot` в `src/App.tsx`): одна и та же логика, поэтому матч с ботом работает и там, где никакого сервера нет.

Важная деталь рендера: состояния от сервера приходят ~30 раз в секунду целыми объектами, поэтому они буферизуются и показываются с задержкой 70 мс — так движение выглядит плавным. Партия, которая считается локально, меняет те же объекты на месте 120 раз в секунду, и её нужно рисовать напрямую. За это отвечает проп `live` у `<Table>` (`live={mode !== "online"}`): без него локальный матч замирает на стартовой расстановке, хотя счёт продолжает идти. Регрессию на это ловит e2e-проверка «practice-only build» через `data-grip`.

## Ягодки и ставки

Валюта называется **ягодками** — теми же вишнями, что в логотипе. Ставка — это ягодки, которые кладут **оба** игрока: сервер списывает их, когда стол заполнился, и отдаёт весь банк победителю. Если соперник уходит из начатой партии, банк достаётся тому, кто остался; если стол распался до начала — ставки возвращаются. Реванш — это новая ставка, и он не начнётся, если кому-то уже не хватает ягодок.

Почему ставят не сами звёзды: звёзды Telegram можно потратить **только в сторону бота**, передать их другому игроку нельзя. Поэтому звёзды покупают ягодки (`shared/wallet.ts`, наборы 100 / 350 / 1000), а ставки идут в ягодках. Новый игрок получает 150 ягодок, чтобы сесть за стол сразу.

- Кошелёк и список столов — в `src/App.tsx` (модалки `wallet` и `tables`), значок ягодки нарисован в `src/Berry.tsx`, баланс виден в шапке мини-приложения и в верхней панели десктопа. На экране игры показывается только ставка стола — никаких лишних подписей.
- Протокол: `hello {key}` сообщает, чей это кошелёк, сервер отвечает `wallet {balance}`; лобби получает `tables [{code, host, avatar, stake}]`; `queue {stake}`, `create {stake}`, `join {code}`, `topup {pack}`.
- Балансы лежат в одном JSON-файле рядом с сервером (`WALLETS_FILE`, по умолчанию `server/.wallets.json`, в git не попадает). Это не база данных: одного процесса хватает для игры, но для реальных денег нужно нормальное хранилище и транзакции.

### Оплата звёздами

Нужен бот и публичный HTTPS-адрес сервера:

```sh
BOT_TOKEN=123:ABC TELEGRAM_WEBHOOK_SECRET=длинная-случайная-строка PORT=8080 npm start
# и один раз:
curl -X POST "https://api.telegram.org/bot$BOT_TOKEN/setWebhook" \
  -d "url=https://пример.ру/api/telegram/длинная-случайная-строка"
```

1. Игрок выбирает набор → сервер вызывает `createInvoiceLink` (валюта `XTR`, пустой `provider_token`, ровно одна цена) → клиент открывает счёт через `WebApp.openInvoice`.
2. Telegram ждёт ответа на `pre_checkout_query` **не дольше 10 секунд** — сервер отвечает сразу.
3. Ягодки начисляются **только** по `successful_payment`, с защитой от повтора по `telegram_payment_charge_id`. Статус из `openInvoice` — лишь подсказка интерфейсу.

Без `BOT_TOKEN` сервер честно отвечает `topup_unavailable`, и кнопка пополнения объясняет, что оплата появится после подключения бота. Для локального демо есть `ALLOW_TEST_TOPUP=1` — зачисляет набор без оплаты (в `npm run dev` он не включён по умолчанию).

**Не проверено:** настоящая оплата звёздами. В этом окружении нет ни бот-токена, ни публичного адреса для вебхука, поэтому проверены только ветки «бот не подключён» и начисление по приходу события. Перед приёмом денег боту нужны `/paysupport`, условия возврата и валидация `initData` (см. ниже).

## Telegram

### Интерфейс внутри Telegram

В Telegram и на телефоне (`max-width: 760px`) интерфейс клуба не показывается. Вместо него открывается компактный Mini App (`src/MiniApp.tsx`, `src/mini.css`):

- **Экран меню:** логотип Amazing Pool, баланс ягодок, счётчик игроков и четыре кнопки — «Играть онлайн», «Игра с ботом», «Играть с другом», «Тренировка». «Играть онлайн» открывает список свободных столов со ставками, «Игра с ботом» сажает соперника сразу и работает даже без сервера. Внизу — правила, история, имя. Ожидание соперника и код комнаты показываются на том же экране.
- **Экран игры:** только стол во весь экран, без подписей и подсказок. Вся обвязка (чей ход, смена вида, заново; в браузере ещё и «назад») прижата к **нижнему краю**: Telegram рисует свои «⋯» и «✕» поверх верхнего угла WebView, а в повёрнутой рамке это ровно тот угол, где была бы верхняя панель. Справа — кий для удара, сверху по центру — табло: аватар и имя каждого игрока (фото из Telegram, иначе буква имени) и сами шары с номерами и цветами, забитые становятся пустыми кружками, восьмёрка стоит между игроками. Рамка вокруг аватара показывает, чей сейчас ход. Пока группы не определены, вместо шаров показаны семь пустых кружков у каждого. В тренировке табло показывает все 15 шаров одной строкой.
- Экран не прокручивается: высота равна `viewportStableHeight`, отступы берутся из `contentSafeAreaInset` и `env(safe-area-inset-*)`.
- Стол всегда горизонтальный: если экран вертикальный, весь игровой экран поворачивается на 90° (`.is-rotated`), и телефон держат боком, как настоящий кий. Касания пересчитываются под тот же поворот, поэтому кий слушается пальца один в один.
- Внутри Telegram собственная кнопка «назад» не рисуется: клиент показывает свою в том же углу. Она же возвращает из игры в меню, а выход из незаконченного онлайн-матча дополнительно спрашивает подтверждение.
- Подписей на столе нет. Единственное исключение — короткое сообщение после фола (почему ход ушёл сопернику), оно гаснет само. Как целиться и как бить, написано на экране правил.
- После партии онлайн предлагается «Сыграть ещё»: новая расстановка приходит, когда её попросили оба игрока (сервер сбрасывает игру только на встречный запрос).

Десктопная версия клуба остаётся для широких экранов.

### Мост SDK

Если страница открыта с `tgWebAppData`, приложение загружает официальный Telegram Web App SDK, вызывает `ready()` / `expand()`, задаёт цвета и использует имя для отображения. Учитывает высоту WebView и безопасные отступы; пока открыт стол, отключает вертикальный жест сворачивания на поддерживаемых версиях SDK, а в онлайн-комнате включает подтверждение закрытия. В обычном браузере ничего из Telegram не требуется.

**Статус проверки:** браузерные UI-тесты и отдельный тест с **моком SDK** есть. Это не проверка настоящего Telegram, WKWebView iOS или Android WebView. До утверждения «готово к Telegram» нужно вручную проверить через бота:

- iOS и Android: загрузка WebGL, 30/60 FPS на целевых устройствах, нагрев и расход памяти.
- Прицеливание пальцем, смена ориентации, края экрана и отсутствие конфликтов со свайпом закрытия.
- Сворачивание/возврат, потеря сети, повторное открытие. Сейчас отключение завершает матч, восстановления нет.
- Первый звук после касания, буферизация снимков на мобильной сети и совместный матч двух телефонов.

**Важно:** `initDataUnsafe` используется только как подпись гостя: оттуда берутся имя и `photo_url` для аватара (сервер пропускает только `https://`-ссылку не длиннее 300 символов и отдаёт её сопернику; если картинка не загрузилась, остаётся буква имени). Серверная аутентификация Telegram пока не реализована, поэтому гостевое имя нельзя считать подтверждённой личностью.

Для публикации:

1. Разверни production-сервер за **HTTPS** с поддержкой WebSocket upgrade и достаточным idle timeout (например 120 секунд).
2. Укажи публичный URL как Mini App / menu button своего бота через BotFather.
3. До публичного рейтинга или аккаунтов добавь серверную проверку подписи и срока действия `initData`, сессии и привязку игрока к проверенному Telegram ID. Токен бота хранится только в серверных секретах, никогда в frontend / репозитории.
4. Добавь БД для пользователей/результатов, reconnect/resume, лимиты запросов по пользователю/IP, ограничения ресурсов и мониторинг.
5. Для нескольких серверов потребуется общий matchmaking и маршрутизация комнат (например Redis), а также нагрузочные тесты.

Приглашение открывается двумя способами: обычной ссылкой `?room=ABCDEF` и Telegram deep link `https://t.me/<бот>/<app>?startapp=ABCDEF`. Второй вариант используется автоматически, если при сборке задан `VITE_BOT_APP_URL`; код комнаты читается из `start_param`, `tgWebAppStartParam` или `?room=`. Сам бот и публичный хостинг в этом репозитории не создаются.

## GitHub Pages + бот

GitHub Pages отдаёт **только статические файлы**: он не может принять WebSocket-соединение и не выполняет серверный код. Поэтому схема такая:

| Что                                   | Где                       | Зачем                              |
| ------------------------------------- | ------------------------- | ---------------------------------- |
| интерфейс, 3D-стол, тренировка        | GitHub Pages              | этот адрес указывается в BotFather |
| очередь, комнаты, авторитетная физика | отдельный хост с `wss://` | игра двух пользователей            |

Пока сервера нет, сборка работает как **тренировочная**: приложение ни разу не пытается открыть WebSocket, в меню видно «Онлайн позже», кнопки онлайна помечены `скоро` и объясняют это при нажатии, а главной кнопкой становится «Тренировка».

Как клиент выбирает адрес (`src/config.ts`, `resolveGameServer`):

1. `?server=wss://...` в адресе страницы — ручная заглушка для проверки будущего сервера; выбор запоминается в localStorage. `?server=off` принудительно оставляет только тренировку, `?server=auto` возвращает поведение по умолчанию.
2. `VITE_GAME_SERVER` из сборки.
3. Локальная разработка (`npm run dev`) — текущий origin через прокси Vite.
4. Иначе один запрос `api/health` к своему origin: отвечает — работаем онлайн, нет — остаёмся в тренировке. На `*.github.io` и подобных статических хостах запрос даже не делается.

### 1. Сборка под Pages

`vite.config.ts` использует относительный `base` (`./`), поэтому сборка одинаково работает и в корне домена, и по адресу `https://<имя>.github.io/<репозиторий>/`. Шрифт и иконка собираются как ассеты с относительными путями, `public/.nojekyll` отключает обработку Jekyll.

Адрес игрового сервера попадает в сборку через переменные окружения (`.env.example`):

```sh
VITE_GAME_SERVER=wss://billiard.example.com npm run build
# необязательно: ссылка на сам Mini App для приглашений
VITE_BOT_APP_URL=https://t.me/your_bot/your_app
```

`VITE_GAME_SERVER` принимает `wss://host`, `https://host` или адрес с путём; `/ws` добавляется автоматически. HTTPS-страница может открывать только `wss://`, обычный `ws://` браузер заблокирует.

### 2. Публикация

В репозитории есть workflow `.github/workflows/deploy-pages.yml`: `npm ci` → `npm test` → `npm run build` → публикация `dist`.

1. Settings → Pages → Source: **GitHub Actions**.
2. Settings → Secrets and variables → Actions → **Variables**: `VITE_GAME_SERVER`, при необходимости `VITE_BOT_APP_URL`.
3. Push в `main` — Pages обновится на `https://<имя>.github.io/<репозиторий>/`.

### 3. Сервер онлайна

Подойдёт любой Node-хост с HTTPS и WebSocket (VPS с nginx и сертификатом, Render, Fly.io, Railway и т. п.):

```sh
npm ci && npm run build && PORT=8080 npm start
```

Нужен проксируемый upgrade для `/ws` и idle timeout больше 30 секунд (клиент шлёт heartbeat каждые 30 с). Этот же процесс умеет раздавать `dist`, если захочешь обойтись без Pages.

### 4. Бот

### Деплой из рабочей ветки, без слияния в main

Сайт Pages у репозитория **один**: что задеплоили последним — то и открывается по адресу. Поэтому ветку можно публиковать, смотреть на телефоне и только потом сливать в main.

1. Один раз разреши ветке деплоить: **Settings → Environments → github-pages → Deployment branches and tags → Add deployment branch or tag rule** → `arena/*` (по умолчанию в списке только `main`, и запуск из ветки падает с `Branch is not allowed to deploy to github-pages due to environment protection rules`).
2. Запусти деплой из ветки:
   - **Actions → Deploy Mini App to GitHub Pages → Run workflow → Branch: своя ветка**, или
   - `gh workflow run deploy-pages.yml --ref <ветка>`, или
   - просто запушь в ветку `arena/**` — такой push уже публикует сайт сам.
3. Откатить = запустить тот же workflow с веткой `main`.

Адрес в BotFather при этом не меняется: он один и тот же для любой ветки.

**Белый экран после деплоя** означает, что Pages отдаёт корень репозитория, а не собранную папку. В корне лежит `index.html` для разработки со ссылкой на `/src/main.tsx` — на статическом хостинге такого файла нет, и страница остаётся пустой. Так бывает, если в **Settings → Pages → Build and deployment** выбран источник _Deploy from a branch_: тогда GitHub запускает свой `pages-build-deployment` и публикует исходники. Нужен источник **GitHub Actions**, а ветка выбирается при запуске workflow. Чтобы это не выглядело поломкой, страница через 5 секунд сама пишет, что загрузилась не та сборка.

1. BotFather → `/newapp` (или Menu Button) → укажи адрес Pages.
2. Открой Mini App с телефона и проверь: запуск, поворот экрана в горизонтальный, поворот кия по сукну, удар боковым кием, смену вида, выход кнопкой «Назад».
3. Приглашение друга даёт ссылку `?startapp=КОД`, если задан `VITE_BOT_APP_URL`.

**Проверено автоматически:** сборка с относительным `base`, раздача из подкаталога (`/<репозиторий>/`), подключение к серверу на другом origin, матч двух клиентов, мобильная вёрстка и мост SDK с моком. **Не проверено:** настоящий Telegram на iPhone/Android, реальный домен с сертификатом, поведение сети мобильного оператора.
